# Information Architecture Audit — 2026-04-21

The current routing shell in `client/src/App.tsx` exposes three overlapping navigation models. The archive admin shell owns the root and many legacy `/admin` aliases, the newer routed banking workspaces live under standalone routes such as `/control-center`, `/operations`, `/teller`, `/trade-finance`, `/ledger-sync`, `/erpnext-sync`, `/identity-channels`, and `/islamic-banking`, and the customer PWA is separated under `/customer/*`.

The primary navigation mismatch is in `client/src/components/ArchiveAdminSidebar.tsx`. The sidebar still reflects the older archive-first menu and agriculture subtree, but it does not expose the newer routed banking workspaces that the application now supports. This means the routes exist, yet they are only partially embedded into the main operating experience.

The shared dark-shell experience for restored banking domains already exists in `client/src/components/ProductShell.tsx`. It provides a reusable left rail, service-health strip, and return-to-core-banking affordance. `client/src/pages/OperationsCenter.tsx` already acts as a bridge page by surfacing restored product domains and explaining why teller, ERPNext, Islamic banking, trade finance, dispute management, and related areas were promoted into explicit workspaces.

The strongest refactor leverage is therefore not to invent a new routing model, but to connect the existing archive sidebar and the product-shell workspaces more directly. The next change should likely expose the newer workspace destinations from the main admin navigation, reduce duplicated route aliases where possible, and make the control-center / operations surfaces feel like first-class destinations within the original shell rather than parallel side routes.

## Shared data model findings

The shared platform contract in `client/src/lib/platform.ts` confirms that the embedding decisions are meant to be data-driven rather than page-local. `OverviewResponse` is the top-level composition contract for the core shell: it packages `ProductSurface[]`, `ServiceHealth[]`, and `PortfolioMetric[]`, which is exactly the data consumed by `OperationsCenter` and `ProductShell` to render the routed workspace rail and service posture.

`ProductSurface` already contains the critical fields needed to unify navigation across the archive shell and the newer workspace shell: a stable `key`, human-readable `title`, `category`, `summary`, `route`, `status`, and backing `services`. This means the sidebar can be refactored to surface newer domains from the same conceptual product model instead of relying on a separate hardcoded archive-only menu.

The operational follow-through contracts are also present. `WorkflowCase`, `OperatorAction`, `AuditEntry`, `ExportJob`, and `AuthContextResponse` define the shared workflow, action-routing, audit, export, and role-context vocabulary used across the routed workspaces. That supports a next-step refactor where newer destinations are not only linked from the main admin navigation, but also summarized through shared live metrics, action queues, and evidence surfaces without inventing one-off page models.

The architecture conclusion is therefore stronger: the current gap is mostly in navigation exposure and shell integration, not in missing shared contract vocabulary. The data model already supports a more unified core-banking experience; the main work now is to wire the archive navigation and first-class workspace entry points to those existing shared contracts.
